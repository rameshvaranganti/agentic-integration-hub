Definition

What is agentic integration?

Agentic integration, also called agent integration or AI agent integration, is the discipline of connecting AI agents to enterprise applications, data, events and other agents so they can take real actions safely.

In traditional integration a developer fixes every call sequence in advance. In agentic integration an agent chooses its next step at runtime, so access has to be governed: agents reach systems through tools exposed with the Model Context Protocol (MCP), delegate to other agents with agent-to-agent (A2A) protocols, and pass through gateways that apply identity, per-tool authorization, approvals and audit. Your existing APIs, integration flows and event brokers still do the mapping, routing and error handling.

At a glance

Traditional vs agentic integration

  • Who decides the calls: developer at design time → agent at runtime, within policy
  • Contracts: APIs and message types → plus tool definitions and Agent Cards
  • Identity: technical users → user + agent + service on every call
  • Controls: auth and quotas → plus per-tool authorization, approvals and kill switches
How it works

How an AI agent integrates with enterprise systems

Every agent action follows the same governed path, whether one agent answers a question or several agents settle an invoice dispute. Each step has a control that integration and security teams can own.

  1. 1Identity

    A goal arrives with an identity

    A user, a schedule or a business event starts the work. The request carries who the user is and which registered agent is acting for them.

  2. 2A2A

    The agent plans and delegates

    The agent breaks the goal into steps and, where another agent owns a domain, delegates a task to it through the A2A protocol instead of calling that system itself.

  3. 3MCP

    It discovers only permitted tools

    Through an MCP gateway the agent sees only the tools its user and role allow, each with a strict input schema, such as get_order_status rather than raw ERP access.

  4. 4Policy

    Policy decides: allow, deny or approve

    Before any call runs, a policy engine checks user, agent, tool, data and amount. High-impact actions pause for a human approver.

  5. 5Integration

    Existing integrations do the work

    Approved calls go through the same managed APIs, integration flows and event brokers other consumers use, with their mappings, retries and error handling.

  6. 6Audit

    Everything is traced and auditable

    One correlation ID follows the request across agents, gateways and systems, so you can answer who did what, for whom, and why.

The four pillars

What it takes to run agents in an enterprise

Agentic integration is more than connecting a model to an API. These four disciplines decide whether agents stay useful, safe and accountable in production.

Pillar 1 · Agent integration

How agents connect

Agents use MCP to call tools and read data, A2A to delegate to other agents, and your existing APIs and events underneath.

  • Narrow, task-shaped MCP tools over managed APIs
  • A2A Agent Cards for agent discovery and delegation
  • Gateways in front of every agent-facing endpoint

How agents work together

An orchestrator agent coordinates specialist agents, deterministic workflows and people to complete multi-step business processes.

  • Long-running tasks, sagas and compensation

Pillar 3 · Governance & policies

What agents are allowed to do

Policies, written as code and enforced at runtime, decide which agent may use which tool, for whom, on what data and up to what limit.

  • Access, action, data and operational policies
  • Human approval and separation of duties
  • Agent registry, ownership and lifecycle reviews

Multi-agent orchestration

Several agents, one governed process

Real business processes cross domains that different teams own. Instead of one all-powerful agent, an orchestrator delegates to specialist agents, each with its own narrow tools and permissions.

Example: a supplier invoice that fails the three-way match. The orchestrator asks the procurement agent to check the purchase order and goods receipt, asks the supplier's agent over A2A for a corrected invoice, and hands the finance agent a payment request. Because the amount is above the approval limit, policy routes it to an accounts-payable manager before anything is posted.

  • Each agent can only use its own domain's tools
  • Permissions narrow at every delegation hop, never widen
  • A human approves what an agent proposes
  • One trace ID links every agent, tool call and approval

Governance & policies

Policy in action: allow, deny or ask a human

Governance works when rules are explicit, versioned and enforced outside the agent, so a confused or manipulated agent still cannot exceed them. This illustrative policy governs a finance agent's payment tool.

# Illustrative policy-as-code (pseudo-YAML)
policy: supplier-payments
applies_to:
  agents: [finance-agent]
  tools:  [create_payment_request]
rules:
  - deny:    user.role not in [ap_clerk, ap_manager]
  - deny:    supplier.status == "blocked"
  - deny:    bank_details_changed_within_days < 30
  - approve: amount > 10000           # human, four-eyes
    approver: role == ap_manager and approver != requester
  - allow:   amount <= 10000 and po_match == "three-way"
limits:
  calls_per_minute: 20
  max_delegation_depth: 2
audit: [user, agent, tool, decision, amount, trace_id]
RequestDecision
Finance agent, for an AP clerk: pay 4,200 on a matched POAllow
Same agent and user: pay 48,000Approve first
Routed to an AP manager who is not the requester
Procurement agent calls create_payment_requestDeny
Tool is outside that agent's scope
Supplier email tells the agent to "pay to our new bank account"Deny + alert
Recent bank-detail change; treated as possible fraud or prompt injection

Policy engines such as Open Policy Agent or Cedar can express rules like these; the gateway, API management layer and system of record each enforce their part.

Security

Defense in depth for AI agents

No single control makes an agent safe. These six layers work together, and each one maps to risks in the OWASP Top 10 for Agentic Applications, from goal hijack (ASI01) to rogue agents (ASI10).

🪪

Identity on every call

User, agent and service identities travel with each request. Tokens are exchanged for narrow downstream scopes, never passed straight through.

ASI03
🔐

Least privilege per tool

Agents discover only the tools they may use, and permissions shrink at every delegation hop.

ASI02 ASI03
🧱

Input and output guardrails

Tool results and agent messages are treated as data, not instructions. Strict schemas, validation and personal-data redaction apply both ways.

ASI01 ASI06
✋

Approvals and kill switches

High-impact actions wait for a person. Any tool or agent can be switched off instantly without a redeploy.

ASI09 ASI10
🤝

Trusted agents and servers

Only registered agents with signed Agent Cards and approved MCP servers are reachable, with pinned versions and owners.

ASI04 ASI07
📈

Audit and observability

Traces across agents, gateways and integration flows, tamper-evident logs and alerts on denied calls, loops and unusual volumes.
